# ResearchOS Attestation Capability
## Implementation Guide (v3)

## Overview

The ResearchOS Attestation Capability provides cryptographically signed, chain-linked attestations that can be called directly from ODK Collect (or any Android application capable of launching Android intents).

The capability is designed to prove:

- who performed an action
- when it occurred
- what data were being attested
- how the operator was verified
- whether an external trusted timestamp was obtained
- that no attestation in the chain has been modified

The capability never signs the raw form.

Instead it signs a SHA-256 hash generated by ODK.

This keeps the interface lightweight while ensuring the attestation is bound to the complete form contents.

---

# Architecture

```
        ODK FORM

        concatenate relevant fields
                  │
                  ▼
          SHA-256 (ODK)
                  │
                  ▼
        event_payload_hash
                  │
                  ▼
         Android Intent
                  │
                  ▼
        ResearchOS Attestation
                  │
                  ▼
      ECDSA Signature + Hash Chain
                  │
                  ▼
       (optional RFC3161 timestamp)
                  │
                  ▼
      returned directly to ODK
```

The attestation therefore proves the integrity of the ODK-computed hash rather than the raw payload.

---

# Recommended ODK Workflow

## 1 Create canonical payload

Create an ODK calculate field that concatenates every field that should be protected.

Example

```
concat(
    ${participant_id},
    '|',
    ${operator_id},
    '|',
    ${event_description},
    '|',
    ${visit_date}
)
```

The concatenated payload itself does **not** need to be stored.

---

## 2 Hash the payload

Immediately hash the concatenated payload.

Example

```
digest(
    concat(
        ${participant_id},
        '|',
        ${operator_id},
        '|',
        ${event_description},
        '|',
        ${visit_date}
    ),
    'SHA-256',
    'hex'
)
```

Store only

```
event_payload_hash
```

This becomes the immutable object that ResearchOS signs.

# Timestamp Policy

```
trusted_timestamp='disabled'
```

No RFC3161 request.

---

```
trusted_timestamp='preferred'
```

Attempt RFC3161.

Continue if unavailable.

---

```
trusted_timestamp='required'
```

RFC3161 timestamp must succeed.

Otherwise the attestation fails.

# Capability Chaining

Verification methods are implemented as independent capabilities.

Example

```
Attestation

        │

        ▼

Verification

        │

 ┌──────┼─────────────┐

 ▼      ▼             ▼

QR     NFC      Fingerprint
```

Attestation does not implement QR or NFC itself.

Instead it calls the relevant capability and incorporates the returned evidence.

# Chain Structure

Each attestation stores

```
previous_attestation_hash
```

forming

```
GENESIS

↓

hash1

↓

hash2

↓

hash3

↓

...
```

Changing any previous record invalidates every subsequent signature.

---

# RFC3161 Timestamping

When enabled the capability requests an RFC3161 trusted timestamp.

Additional returned fields include

```
trusted_timestamp_status

trusted_timestamp_authority

trusted_timestamp_time_iso

trusted_timestamp_serial

trusted_timestamp_attested_hash

trusted_timestamp_token_sha256

trusted_timestamp_token_base64
```

The Base64 token can be independently verified later.

---

# Security Model

ResearchOS never receives the original protected payload.

Instead it receives only

```
SHA256(payload)
```

ResearchOS signs

```
SHA256(payload)
```

not

```
payload
```

This avoids transmitting sensitive data while still providing cryptographic integrity.

---

# Offline Behaviour

Offline

- local signature created
- chain maintained
- no RFC3161 timestamp

Online

- local signature created
- chain maintained
- RFC3161 timestamp obtained if requested

---

# Recommended Verification Workflow

Later, in R

1. Recreate each canonical payload from the exported ODK data.
2. Compute SHA-256.
3. Compare with `event_payload_hash`.
4. Verify every ECDSA signature.
5. Verify every previous hash link.
6. Verify RFC3161 timestamps (if present).
7. Report any failures.

This demonstrates:

- data integrity
- provenance
- operator verification
- temporal consistency
- complete attestation chain integrity

---

# Design Principles

- Capabilities are independent.
- Capabilities may call other capabilities.
- Intent-driven execution requires no intermediate user interaction.
- ODK computes hashes.
- ResearchOS signs hashes.
- Verification evidence is cryptographically bound into the attestation.
- Server timestamps are optional.
- Offline operation is fully supported.
- The capability returns a compact flat structure suitable for direct storage in ODK.
